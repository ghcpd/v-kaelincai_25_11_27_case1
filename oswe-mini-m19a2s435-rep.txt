## 📋 Appointment lifecycle & crash points
Appointment lifecycle states:
- INIT (logical start)
- IN_PROGRESS (DB reserved, outbox entry created)
- SUCCESS (calendar confirmed, appointment persisted, outbox done)
- FAILURE (rolled back or compensated)
- CANCELLED (compensated)

Flow (Controller → outbox → calendar):
1. Client POST -> /appointments/confirm with `client_request_id` (idempotency key).
2. Check idempotency: if same client_request_id -> return prior state (success/202/500) no double book.
3. Create appointment record in the DB as IN_PROGRESS and add an outbox entry for CREATE_CALENDAR.
4. Try to sync with calendar synchronously (fast-path):
   - If calendar returns success -> set appointment SUCCESS, mark outbox DONE, return 200.
   - If calendar times out/fails -> attempt compensation: cancel calendar booking (if one exists) and delete/roll back appointment to prevent false positives. Return 500 or optionally 202 depending on the policy.
5. Outbox worker (background) retries pending outbox items; circuit breaker prevents continuous retries if calendar is down. On repeated failure, mark FAILED in OUTBOX and set appointment FAILURE or IN_PROGRESS (depending on policy and design).

Crash points and root causes (found during analysis):
- calendar_adapter: timeouts/unhandled exceptions bubble up to controller -> 500 responses.
- no idempotency: repeated retries can create multiple DB rows + multiple calendar reservations.
- improper transactional semantics: DB insertion occurs and calendar fails, leading to inconsistent state.
- no compensation flow: created calendar entry and DB inconsistency remain if synchronous code fails.

## ✅ Recommended fixes implemented
- Idempotency key: controller-level check for `client_request_id`, unique DB constraint ensures single outcome for repeated calls.
- Retry & backoff: calendar_adapter uses async retries with exponential backoff – configurable per-call.
- Circuit breaker: counter-based simple circuit breaker to avoid repeated calls when the calendar is down; the adapter returns a `CircuitBreakerOpen` error.
- Transactional outbox: appointment created with an outbox entry; synchronous attempt attempts to complete the operation; outbox worker processes pending entries — helps ensure eventual consistency.
- Compensation/Cancel: If calendar booking is partially created and DB fails, app tries to cancel calendar booking; outbox includes CANCEL action support.
- Unified state machine: appointments are recorded as `IN_PROGRESS` -> `SUCCESS` / `FAILURE` / `CANCELLED`.
- Structured logging: loggers write JSON with `appointment_id`, `client_request_id`, `event`, `message`, and `details` payload (PII redacted).
- Tests: 5 test scenarios + a single-run harness to exercise flows and assert correctness.

## 🧪 Integration test scenarios (in `tests/integration/appointment_cases.yaml`)
1. Normal success:
   - Mode: default
   - Expect: HTTP 200, DB exists, status SUCCESS.

2. Calendar timeout -> 500 with no booking:
   - Mode: 'timeout' (mock calendar delays to force HTTPX timeout)
   - Expect: HTTP 500, no DB appointment (rollback occurred, preventing booking).

3. Idempotent retry avoids double booking:
   - Post the same `client_request_id` twice (client retry).
   - Expect: First OK (200), second returns previous status, DB contains exactly one appointment.

4. Partial success triggers compensation:
   - Mode: 'malformed' (mock calendar returns invalid JSON -> error)
   - Expect: API returns 500 and no booking exists in DB (compensated or rolled back).

5. Audit and reconciliation:
   - Normal success; ensure logs contain `appointment_id` and `client_request_id` and the expected `event` keys.

## 💡 Design notes, tradeoffs & considerations
- Sync-first approach: to return success synchronously when calendar is immediately available; if not, roll back appointment to avoid false positives.
- Two-phase or outbox-based approach avoids double-booking, and provides compensation for calendar-created reservations if DB transaction fails.
- We choose a simple in-memory HTTP-based mock calendar (HTTP mode control for `timeout`/`error`/`malformed`) to avoid depending on third-party services.
- For production: consider using:
  - Real persistent DB + transactions with logical lock or unique constraints for IDs.
  - Stronger circuit breaker libraries and exponential backoff libraries (e.g., Tenacity).
  - Observability: trace context propagation (e.g., OpenTelemetry) for cross-service tracing.
  - Queue-based outbox with requeue/failure policies.

## Security & other notes
- Logs redact patient names, avoid storing PII raw.
- Idempotency keys should be cryptographically random or generated server-side to protect from collisions & abuse.
- Outbox worker needs monitoring and an alerting policy for FAILED outbox entries.
