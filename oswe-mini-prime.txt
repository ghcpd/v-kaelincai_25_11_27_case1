## Appointment lifecycle (map) and crash points 🔍

Lifecycle: INIT → IN_PROGRESS → CONFIRMED / CANCELLED (FAILED)

- Client submits POST /api/appointments with `Idempotency-Key` header:
  - Controller logs `request_received`.
  - Idempotency check:
    - If key exists and response was previously recorded → return recorded response (safe).
    - If key exists and no recorded response yet → return 202 in-progress.
  - Create Appointment with state = IN_PROGRESS.
  - Optionally, if client wants async (header `Prefer: respond-async`), enqueue Outbox & return 202 (IN_PROGRESS).
  - Synchronous booking flow:
    - Adapter `CalendarAdapter.book` is called (timeout, retry and circuit breaker behavior).
    - On success: appointment state -> CONFIRMED, idempotency record response is stored, return 200.
    - On failure or timeout: compensation occurs (appointment cancelled (CANCELLED)), idempotency response stored accordingly, return 500.

Crash points identified in the lifecycle:
1. Uncaught exceptions from the calendar adapter (RequestException) that bubbled to client.
2. Timeouts from calendar requests that were not handled (led to errors/ partial states).
3. Missing idempotency: repeated requests created new records causing double booking.
4. No transactional outbox/compensation: partial success (local DB wrote) but external sync failed — no rollback or compensation.

## Concrete fixes implemented ✅

- Idempotency:
  - `IdempotencyKey` store that records the `key`, `appointment_id`, and `response`.
  - On repeated requests with same key, responses are re-sent (or `202` if in-progress).
  - Ensures repeated calls with same idempotency key are not creating duplicate appointments.

- State machine:
  - `AppointmentState` enum: `INIT/IN_PROGRESS/CONFIRMED/CANCELLED/FAILED`.
  - Explicit `create_appointment`, `mark_confirmed`, `mark_cancelled`, and `mark_failed`.

- Compensation & Outbox:
  - Synchronous path cancels local reservation if calendar sync fails.
  - Outbox worker for asynchronous processing and retries; on max retries failure, outbox triggers a compensation (cancels appointment).
  - When clients request `Prefer: respond-async`, the system returns 202 and the outbox worker ensures eventual state.

- Calendar Adapter resiliency:
  - Implemented request-level timeouts, retry logic, and a simple circuit-breaker based on consecutive failures.

- Structured logging & audit:
  - Events are logged as JSON lines to `logs/appointments.jsonl` with `timestamp`, `event`, `appointment_id`, `request_id`, `idempotency_key`, `state`, and `message`.
  - `logs/audit_schema.json` defines schema & examples.

- Observability:
  - GET endpoints to inspect:
     - GET /api/appointments/<appointment_id> — check appointment state & slot.
     - GET /api/appointments?slot=<slot> — list appointments.
     - GET /api/idempotency/<key> — check idempotency entry and stored response.

## Test plan — integration scenarios (implemented) ✅

All scenarios are defined in `tests/integration/appointment_cases.yaml`:

1) normal_success
   - simulate: none
   - Expected: 200, appointment state CONFIRMED

2) calendar_timeout
   - simulate: timeout (mock calendar times out)
   - Expected: 500, appointment state CANCELLED (compensation checks)

3) idempotency_retry
   - simulate: none
   - Send POST twice with identical `Idempotency-Key` (retries=2)
   - Expected: both calls return the same appointment id (no double booking) and final state CONFIRMED

4) partial_success_compensation
   - simulate: fail (mock calendar returns 500)
   - Expected: 500 returned; appointment state CANCELLED (compensation)

5) audit_verification
   - simulate: none
   - Expected: logs contain `appointment_created`, `calendar_book_*` attempt, and `appointment_confirmed` — used for audit verification.

6) async_in_progress
   - Preferred async handling: header `Prefer: respond-async`
   - Initial response 202; background outbox worker should mark the appointment CONFIRMED later (poll & assert).

Integration tests are run via run_suite.py which:
- Starts the mock calendar and API,
- Executes each scenario,
- Verifies HTTP responses and calls the API to inspect the appointment state (via GET),
- Reads log snippet from `logs/appointments.jsonl` for audit assertions,
- Prints summary (PASS/FAIL + metrics).

## Structured log schema 📄

Located: `logs/audit_schema.json` (also summarized here):

- timestamp: ISO8601 UTC
- level: INFO/ERROR
- event: e.g., appointment_created, calendar_exception, appointment_confirmed, idempotency_marked
- appointment_id
- request_id
- idempotency_key
- state
- message
- extra (e.g., retry count, attempt, last_error)

This makes it easier to reconcile logs for audit and to write automated queries for reconciling slots and duplicates.
