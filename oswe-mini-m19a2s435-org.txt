What I changed/implemented (mapping & fixes)
- Appointment lifecycle:
  - INIT -> IN_PROGRESS -> SUCCESS / FAILED
  - For synchronous confirm: the API creates appointment in a transaction then attempts the calendar sync, only commits success after calendar confirmation; failures trigger deterministic rollback returning 500 (or a failed idempotency response).
  - For async confirm: the API persists appointment in IN_PROGRESS and writes to `outbox`. A background worker polls the outbox to sync to calendar with retries/backoff. On repeated failures, compensation is triggered and the appointment is set to FAILED and the slot “released”.
- Idempotency:
  - An `IdempotencyRecord` table keyed by `client_request_id` stores the final response payload/status; duplicate calls return the stored result to avoid double bookings.
  - On async-mode, `client_request_id` prevents creating duplicate DB entries or scheduling duplicate outbox messages.
- Retry/backoff & compensation:
  - Outbox worker attempts calendar sync; `attempts` increments and when `attempts >= max_attempts` it compensates (fails appointment and deletes/cleans outbox).
  - For test speed, `max_attempts` is small (2) to validate compensation quickly. This should be configurable in production.
- Timeouts & Circuit Breaker:
  - Calendar adapter uses HTTP client timeouts; timeouts raise a CalendarError handled by the service.
  - Production recommendation: add a circuit breaker (e.g., pybreaker, AWS ApiGateway or internal CB) with metrics & thresholds; I did not implement that to keep this minimal/testable.
- Structured logs:
  - `audit_log()` writes JSON (`timestamp`, `level`, `message`, `appointment_id`, `request_id`, `extra`, service) into `logs/audit.log`.
  - `REDACT_FIELDS` list redacts specified sensitive fields in the `extra` payload.
